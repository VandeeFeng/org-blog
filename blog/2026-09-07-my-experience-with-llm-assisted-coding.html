Maintain useful patterns

SKILL: https://github.com/affaan-m/everything-claude-code/blob/main/commands/learn.md

在解决实际的代码问题的时候，有许多方案是可以固定下来复用的。

根据这个 SKILL，我设计了一个 learned skill。learn skill 会固有价值的 pattern，生成 learned skill。learned skill 的 SKILL.md 是其他 learned skill 的 index。

不选择把 learned skill 生成单独的 skill 文件夹是因为它们的普遍性不强，也经常要更新和修改，不能完全当作 SKILL 来设计。

Learn skill： 

---
name: learn
description: Extract reusable patterns from sessions into Phi learned skills. Use when the user asks to extract learning, save a reusable pattern, preserve an error resolution or debugging technique, or invokes /skill:learn. `[SKILL Path]/learned/SKILL.md` is the index of all learned skills.
---

# Learn Skill

Dynamically extract and store reusable patterns as skills.

`[SKILL Path]` refers to Phi's skill root: `~/.phi/skills`.

## Quick Start

When user wants to extract learning from current session:

1. Review session context for extractable patterns
2. Identify the most valuable/reusable insight,list them
3. Ask user for confirmation before creating skill file
4. Create `[SKILL Path]/learned/[skill-name].md` using [templates/learned-skill-template.md](templates/learned-skill-template.md)
5. Update `[SKILL Path]/learned/SKILL.md` using [templates/learned-SKILL.md](templates/learned-SKILL.md)
6. Update the total skills number in SKILL.md.

## What to Extract

### 1. Error Resolution Patterns
- What error occurred?
- What was the root cause?
- What fixed it?
- Is this reusable for similar errors?

### 2. Debugging Techniques
- Non-obvious debugging steps
- Tool combinations that worked
- Diagnostic patterns

### 3. Workarounds
- Library quirks
- API limitations
- Version-specific fixes

### 4. Project-Specific Patterns
- Codebase conventions discovered
- Architecture decisions made
- Integration patterns

## Quality Guidelines

### DO Extract:
- Error patterns that occur more than once
- Non-obvious debugging techniques
- Workarounds for library quirks
- Architecture decisions and their rationale
- Integration patterns across services/tools

### DO NOT Extract:
- Trivial fixes (typos, simple syntax errors)
- One-time issues (specific API outages, temporary glitches)
- Obvious solutions (standard library usage without special context)
- Information already well-documented elsewhere

### Tips for Quality Skills
1. **Be Specific**: Narrow trigger conditions = better matching
2. **Include Examples**: Code snippets make patterns actionable
3. **Document Why**: Explain the problem, not just the solution
4. **Keep Focused**: One pattern per skill
5. **Use Descriptive Names**: Names should indicate what the skill solves


## Skill File Format

### Individual Skill Files

Use the template file [templates/learned-skill-template.md](templates/learned-skill-template.md) as the base for all learned skills.

Key sections:
- **Frontmatter**: name and description (critical for skill discovery)
- **Problem**: What specific issue this solves
- **Solution**: Actionable steps to implement
- **Example**: Code snippet if applicable
- **When to Use**: Trigger conditions for activation
- **Related Patterns**: Cross-references to other skills

### SKILL.md

Use [templates/learned-SKILL.md](templates/learned-SKILL.md) as the base for maintaining the learned skills index.

Purpose:
- Provides a categorized listing of all learned skills
- Enables easy browsing and discovery of patterns
- Tracks skill count and update timestamp

Update SKILL.md whenever saving a new skill.

## Extraction Process

### Step 1: Resolve Phi Context

1. Use `session-info` to retrieve the current Phi session ID, title, and session reference.
2. Call `memory_check` and read its `Path:` value to resolve the current Phi project memory directory.
3. Use `memory_search` when related project memories may contain prior decisions or existing patterns.
4. Review the current conversation and available project context.

Look for:
- Repeated error fixes
- Non-obvious solutions
- Workarounds discovered
- Best practices learned

### Step 2: Identify Pattern

Ask yourself:
- Is this reusable? (Will save time in future sessions)
- Is this non-trivial? (Not typos or simple syntax errors)
- Is this generalizable? (Not one-time issues)

Prioritize patterns that:
- Solve common problems
- Apply across multiple projects
- Document non-obvious solutions

### Step 3: Draft Skill

Use the skill file format above.

**Naming Convention:**
- Use kebab-case for skill names
- Make names descriptive but concise
- Example: `async-error-handling-pattern`, `docker-volume-permission-fix`

**Frontmatter:**
```yaml
---
name: [skill-name]
description: Use when [trigger conditions]. Covers [specific problem/solution].
---
```

The description is critical - it's what helps the skill system know when to load this skill.

### Step 4: Validate

Before presenting to user:
- Check that the skill has clear trigger conditions
- Ensure the solution is actionable
- Verify code examples are correct
- Confirm the pattern is truly reusable

### Step 5: Present and Save

Show the user:
1. Pattern name
2. Brief description of what was extracted
3. Why it's valuable

Ask user question: "Save this pattern to learned skills?"

If yes, save to `[SKILL Path]/learned/[skill-name].md`, or use:

```bash
scripts/save-learned-skill.sh <skill-name> <draft-file>
```

### Step 6: Update `learned/SKILL.md`

Add the new skill to the index section.

## Common Use Cases

### User runs the Phi skill command
```
User: /skill:learn
```
1. Review session for extractable patterns
2. Present candidate patterns to user
3. Ask which to save
4. Save selected patterns

### User asks to extract specific topic
```
User: Extract what we learned about async error handling
```
1. Search session context for async/error patterns
2. Compile findings
3. Generate skill file
4. Present and save

### User wants to capture architecture decision
```
User: Save the event sourcing pattern we used
```
1. Extract the pattern details
2. Document rationale and trade-offs
3. Create skill with example code
4. Present and save

## Integration with Other Skills

This skill works well with:
- **session-info**: Retrieve the current Phi session metadata and reference.
- **memory_check**: Resolve the current Phi project memory directory.
- **memory_search**: Find related project memories before extracting duplicate patterns.
- **skill-creator**: Create complex bundled skills with scripts or references.

Experience

LLM 生成的代码很容易出现这些问题：

  • 不准确、不合适的语义命名
  • 意义不大的 wrapper 或 projection、完全可以 inline 的独立函数
  • 重复的业务逻辑，重复的代码，legacy 代码
  • 按照答案出题目的 test

很多 slop 代码在中文里看起来就像：我现在想了一下，我决定就按照一个还比较喜欢的方式来进行这次的写作。

让我印象最深的是之前 pi-memory-md 的时候，用自然语言要求 agent 完成一段获取 memory 目录的逻辑。搞了一大堆复杂的文件、文件夹路径逻辑，还写了能够跑通的 test，其实只需要利用 git rev-parse --show-toplevel 就可以了。

对于代码量很大，业务逻辑复杂的实现，一次 session 的上下文窗口不够，需要分段实现或多 agent 合作，自然语言到代码逻辑之间的损耗变大了很多。就算写好了明确的 plan 和 design，也很难保证代码质量和业务逻辑的完整。

比如在实现 phi memory graph 的时候，让 agent 按照已经写好了设计文档执行。一看代码，就是把之前 phi memory 的部分实现换了个名字，写了几个新的结构体，大量的重复性包装，完全没有按照文档实现新的 graph 架构。还有重构 phi SDK public 和 private API 边界时大量的重复代码逻辑和无意义包装，等等。

现在最适合我的方式：半自动让 LLM 填空。自己写好函数、结构体的命名语义，固定好代码逻辑骨架和业务框架，拿不准、不会写的细节用伪代码，再交给 LLM 填空。

My AGENTS.md

AGENTS.md + SKILL:cooking

全放在 AGENTS.md 里有点影响一般的对话，而且也太长了，所以分开了。效果感觉比放一起要好。

其中这几条我觉得效果很好：

  • Clearly define what done means before starting review.

    让 agent 有明确的执行目标和验证标准。模型似乎对这句话非常敏感，有和没有这句话的区别在我的使用体验里很大。

  • Propose ASCII drawings to explain complete systems. Use examples when possible.

    日常对话或是生成文档的时候，都很有用。

  • Treat member visibility changes as a breaking design shift. Keep all fields and functions private unless external access is strictly required by the design. Prompt the user for explicit approval before changing any access modifier from private to internal or public.

    减少外部代码对内部实现的依赖，避免扩大可见范围。

  • Use property-based testing: define constraints of what should never happen, then generate relevant test cases that attempt to break those constraints.

    极大的提升了测试的有效性。 

# Vandee's AGENTS.md

IMPORTANT: Always thinking in English. Write all code in English. Respond to the user in the user's language.

KEEP YOUR RESPONSES FOCUSED AND CONCISE!

AVOID SUPERLATIVES and PRAISE. Stop telling me I am absolutely right. Give me the cold hard truth.

When writing something intended for human consumption, (comment, commit message, reply to prompt) use as few words as possible. Pick every word meticulously to reduce the volume to a strict minimum. Be down to the point. Less is more.

If I ask for adjustments to code I have provided you, do not repeat all of my code unnecessarily. Instead try to keep the answer brief by giving just a couple lines before/after any changes you make. Multiple code blocks are ok.

ALL TEMPORARY TEST FILES MUST BE CREATED IN `/tmp/`!!!

RESPECT MY PRETTIER PREFERENCES when you provide code.

- NEVER assume missing context. Ask questions if uncertain.
- When you encounter complex tasks or a plan, break it down into phases.
- You are prohibited from accessing the contents of any .env files within the project.
- Avoid excessive comments in the code blocks. Only critical comments are included. Comment "why" not "what", lowercase commit titles (max 50 characters)
- Use descriptive names and avoid abbreviations or magic numbers
- Use enums instead of booleans for function parameters.
- Avoid magic numbers and strings by extracting recurring or meaningful values into descriptive constants (const) or enums. Keep self-explanatory, one-off values inline to avoid clutter. If a value comes from a spec (e.g. HTTP 200 OK), use a constant regardless.
- Avoid unnecessary inline implementations and excessive abstraction，while separating code into functional cores and imperative shells makes it more testable, maintainable, and adaptable.
- Don't touch blocks of code unrelated to the feature you implement. Don't add comments to a block of code if you did not create it or modify it. As much as possible try to minimize the number of changed lines when implementing a feature.
- Treat member visibility changes as a breaking design shift. Keep all fields and functions private unless external access is strictly required by the design. Prompt the user for explicit approval before changing any access modifier from private to internal or public.
- Avoid emojis and hardcoded secrets
- Propose ASCII drawings to explain complete systems. Use examples when possible.

# Semantic Coherence

- Start with the whole, not isolated parts: establish shared concepts, responsibilities, relationships, and vocabulary to guide both plans and code changes.
- Derive names and structure from that shared model; do not invent terminology independently for each function, struct, or field.
- Ground the semantic model in the module’s overall functionality and business logic; ensure its concepts and relationships faithfully reflect what the module implements.
- Clear variable and function names, Less than 30 characters.

# Code Quality Principles

Universal coding standards

## 1. KISS (Keep It Simple, Stupid)

- Simplest solution that works
- Avoid over-engineering
- No premature optimization
- Easy to understand > clever code

## 2. DRY (Don't Repeat Yourself)

- Extract common logic into functions
- Create reusable components
- Share utilities across modules
- Avoid copy-paste programming

## 3. YAGNI (You Aren't Gonna Need It)

- Don't build features before they're needed
- Avoid speculative generality
- Add complexity only when required
- Start simple, refactor when needed

## Coding Style Preferences

- Prefer K&R Style Pointer Declarations in C.

### Error Handling

- Prefer throwing exceptions instead of returning status codes when handling errors
- Handle all error scenarios with meaningful messages
- Avoid nested ternary operators - prefer switch statements or if/else chains for multiple conditions

# Review & Test Constraints

- Clearly define what done means before starting review.
- When plan phase completed or huge code changed, review its affected business flow without unrelated refactoring: inline unnecessary helpers, consolidate duplicate logic, simplify functions/structs.
- Go slowly. Protect critical path coverage on the business chain first.
- Remove transient or redundant tests while retaining core business-flow, edge-case, and regression coverage. Some tests are incidental regression coverage that may no longer be needed. Prune obsolete tests，not beautify test code.
- Do not decide from what the test code asserts. Infer necessity from the production logic it covers.
- Use property-based testing: define constraints of what should never happen, then generate relevant test cases that attempt to break those constraints.
- Define test scope by the boundary being verified, not by test location.
- Prefer inline tests in the same file when supported. Split into a separate test file only when the source grows too large (more than 3000 lines).
- For a larger module (e.g. `module/`), keep per-file unit tests with their sources; put the module’s top-level / orchestration tests in one place under that module (e.g. `module/tests/`).
- Use separate integration-test directories only for true cross-module cases that no single module owns.
- Test observable behavior, not implementation details. Never widen production API visibility merely to relocate tests.
- If the prompt indicates that a bug is being fixed, don't write the fix right away. First write the test. Observe it failing. Then write the fix. And observe the test passing.

# Development Guidelines

- Follow SOLID principles and prefer composition over inheritance
- Use dependency injection for testability
- Apply repository pattern for data access and strategy pattern for algorithms
- Search codebase first when uncertain
- Use TDD only for complex, critical functionality.
- Make atomic commits for each completed feature stage and push
- Strictly adhere to the layered boundary hierarchy: each layer may only communicate with its immediate neighbor directly below it. Never "punch holes" through layers (e.g., controllers or UI components must never directly call database queries, raw hardware drivers, or low-level network clients; always route through the intermediate service/abstraction layer).

# Technical Preferences

- Prefer UV for python issues and packages.
- Use pnpm for Node.js packages.
- Merge PRs with merge commits
